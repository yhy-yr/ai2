# LocalCare AI 全系统审查

日期：2026-06-19

## 结论

当前版本适合作为本地课程演示，但不适合直接部署到真实环境或处理真实患者数据。

- 严重：3 项
- 高优先级：8 项
- 中优先级：10 项
- 低优先级：5 项

最先要处理的是：撤销泄露的外部 API 凭据、密码加密、把物理删除改成真正的归档、补数据库约束和状态机。

## 审查范围

- 前端：Vue 路由、三角色工作区、28 个 workflow 页面、公共组件、表单、状态与响应式样式
- 后端：14 个 Controller、12 个主要 Service、认证、数据库初始化和配置
- 流程：登录/注册、管理员维护、患者 AI 问诊和预约、医生接诊、病历、处方、检查、患者查看结果
- 验证：`npm run build`、`mvn test`、`npm audit`、关键 API 权限烟雾测试、源码数据流审查

## 验证概况

1. 前端生产构建通过。
2. 后端编译和 `mvn test` 通过，但项目没有任何测试用例，实际执行测试数为 0。
3. API 权限基础校验有效：患者请求管理员预约接口会被拒绝。
4. 未登录调用 `/api/ai/risk` 会成功，当前风险评估接口是公开接口。
5. 认证失败和越权都返回 HTTP 200，仅在 JSON `code` 中表达失败。
6. `npm audit` 发现 1 个高危和 1 个中危依赖问题，涉及当前 Vite/esbuild 版本。
7. 视觉截图受本地浏览器安全策略阻止，因此没有完成逐页像素级视觉验证。

## 严重问题

### C1. 配置文件包含外部 AI API 凭据

`src/main/resources/application.yml` 给 `DEEPSEEK_API_KEY` 配置了一个非空默认值，且 README 明确声称密钥不会写入代码，两者互相矛盾。

风险：凭据一旦进入代码、压缩包、作业提交或版本历史，就应视为已经泄露，可能产生费用和数据外发风险。

建议：立即在服务商侧撤销并重新签发；代码中默认值必须为空；使用环境变量或密钥管理服务；检查历史提交和分发包。

### C2. 用户密码明文保存和比较

`AuthService` 直接比较明文密码；管理员新建医生/患者时统一写入 `123456`；演示账号也使用同一弱密码。

风险：数据库泄露会直接暴露所有账号密码；默认密码没有强制首次修改机制。

建议：使用 BCrypt/Argon2；新账号使用一次性随机初始密码或邀请流程；首次登录强制改密；增加登录限流和失败锁定。

### C3. “归档记录”实际执行不可恢复的物理删除

前端将医生、患者、科室、药品操作标记为“归档记录”，后端却执行 `DELETE FROM`。数据库没有外键，预约、病历、处方、检查可能继续保留对已删除实体的 ID。

风险：医疗记录链路断裂、历史数据在 JOIN 查询中消失、无法追溯，且用户对操作结果的理解与实际行为不一致。

建议：改成软删除/停用字段；历史诊疗实体禁止物理删除；增加外键和明确的 `RESTRICT` 规则；真正删除必须单独设计数据保留策略。

## 高优先级问题

### H1. 前端没有按角色限制 workflow 查询参数

`WorkspaceHome.vue` 根据 `?workflow=` 直接选择组件，没有检查该 workflow 是否属于当前角色。任意已登录角色可通过 URL 打开其他角色的管理界面，后端虽然会拦截多数数据操作，但界面会暴露错误入口和内部功能结构。

建议：为每个角色建立 workflow 白名单；非法 workflow 重定向到角色首页；后端权限仍保持为最终防线。

### H2. 预约状态没有服务端状态机

服务端只验证状态值属于四个枚举，没有限制合法转换。医生或管理员可以把任意预约直接改为 `COMPLETED`、`CANCELLED`、`PENDING` 或重新打开；患者也可以取消 `IN_PROGRESS` 的预约。

风险：绕过“病历/检查/处方完成后才能结束接诊”的前端规则，产生不一致诊疗状态。

建议：在服务端实现状态机，例如 `PENDING -> IN_PROGRESS -> COMPLETED`；取消只允许在规定状态和时间范围内；重新打开应记录原因和操作者。

### H3. AI 问诊完成状态错误地按患者全局计算

患者进度和医生接诊闭环都用 `patient_id` 判断是否存在任意 AI 问诊记录，而不是判断当前预约关联的 AI 问诊。患者历史上做过一次 AI 问诊后，后续所有预约都会显示该步骤已完成。

建议：给 `ai_consultations` 增加 `appointment_id`，或预约创建时显式绑定本次 AI 问诊记录。

### H4. 数据库缺少外键、唯一约束和业务检查约束

所有业务表只保存裸 ID，没有外键。预约时段也没有数据库唯一约束。

风险：孤儿记录、重复预约、无效关联和并发条件下的数据损坏。

建议：补齐外键；为有效预约建立医生+日期+时段的唯一控制；为状态、库存、数量增加检查约束或等效服务端保护。

### H5. 并发下可能重复预约或扣成负库存

预约采用“先 COUNT 再 INSERT”，没有事务锁或唯一约束；处方采用“先读库存再扣减”，更新时没有 `stock >= quantity` 条件。

建议：预约依赖数据库唯一约束并捕获冲突；库存使用原子更新 `UPDATE ... SET stock = stock - ? WHERE stock >= ?`，检查影响行数。

### H6. 会话令牌存储在 localStorage

任何前端 XSS 都可读取 `sessionToken`。同时会话有效期固定一天，没有轮换、设备撤销列表或主动清理过期会话的机制。

建议：生产环境使用 Secure、HttpOnly、SameSite Cookie；增加会话轮换、全端退出和定期清理。

### H7. 依赖存在已知漏洞

`npm audit` 报告当前 Vite 链路存在高危问题，esbuild 存在中危问题。

建议：升级到修复版本并重新执行构建、开发服务器和浏览器回归测试；开发服务器不要暴露到不可信网络。

### H8. 医疗数据外发缺少明确同意和隐私说明

症状描述会发送到 DeepSeek 生成问诊结果或病历草稿。界面有“AI 仅供参考”声明，但没有说明数据会发送给第三方、保存多久、如何撤回或选择仅本地规则模式。

建议：发送前展示明确的数据处理说明和同意项；支持关闭云端 AI；最小化发送字段；制定日志与数据保留策略。

## 中优先级问题

### M1. 所有业务错误都返回 HTTP 200

未登录、越权和业务校验失败均返回 200，只通过 JSON `code` 表示失败。监控、代理、浏览器缓存和标准客户端无法正确区分错误类别。

建议：未认证返回 401、越权返回 403、参数问题返回 400、资源不存在返回 404、冲突返回 409。

### M2. 全局异常会把底层异常文本直接返回前端

`GlobalExceptionHandler` 直接使用 `Exception.getMessage()`，可能暴露 SQL、字段名、连接信息或内部实现。

建议：客户端只返回稳定错误码和通用文案；详细堆栈只写服务端日志并附追踪 ID。

### M3. CORS 对全部来源开放

`allowedOriginPatterns("*")` 允许任意站点调用 API。当前自定义请求头会触发预检，但这不应作为安全边界。

建议：按环境配置可信前端域名；生产环境禁止通配来源。

### M4. README 与实际系统不一致

- README 写后端 8082，实际是 8081。
- README 数据库名使用 `localcare1_ai`，配置使用 `localcare_ai`。
- README 示例路由 `/admin/dashboard` 等不存在，实际统一为 hash 下的 `/workspace`。
- README 声称密钥不在代码中，但配置存在非空默认值。

### M5. 注册表单的邮箱字段被静默丢弃

前端收集可选邮箱并提交，后端没有读取或存储该字段。用户会误以为邮箱已保存。

建议：要么删除邮箱字段，要么补数据库列、校验、唯一性和隐私用途说明。

### M6. 输入校验不足

手机号没有格式校验；用户名、姓名、症状等缺少明确长度限制；预约只校验日期不早于今天，没有校验当天已过去的时段。

建议：前后端统一校验规则，并以服务端为准；数据库字段长度错误应转成清晰业务提示。

### M7. 缺少分页和查询上限

预约、病历、处方、检查、患者、医生等接口一次返回全部记录，数据增大后会影响数据库、网络和页面渲染。

建议：所有列表统一支持分页、排序和服务端搜索。

### M8. 自动化质量门槛不足

后端没有测试；前端没有 test、lint 或 typecheck 脚本。当前“构建通过”不能证明角色权限、状态流转和数据一致性正确。

建议：优先补认证/权限、预约状态、库存、归档、病历关联的集成测试，再补关键 Vue 组件和端到端流程。

### M9. 移动端信息顺序不合理

宽度小于 1120px 时，左侧患者面板、主内容、右侧 AI 面板按纵向堆叠。主工作区会被完整侧栏推到下方。

建议：窄屏把两侧栏改为抽屉或折叠面板，主任务内容保持首屏优先。

### M10. 单文件过大，修改风险高

`VisitWorkspace.vue` 超过 1300 行，`LoginPage.vue` 超过 1000 行，多个页面超过 500 行；数据库初始化器超过 750 行。

建议：按表单、弹窗、数据加载和领域服务拆分；把建表迁移到 Flyway/Liquibase。

## 低优先级问题

### L1. 状态筛选只通过颜色表达选中状态

多个筛选按钮没有 `aria-pressed` 或 `aria-selected`，屏幕阅读器难以知道当前状态。

### L2. 错误和成功消息多数没有实时区语义

全项目只有登录页少量消息使用 `aria-live`；异步错误、保存成功和加载完成通常不会主动通知辅助技术。

### L3. 全局键盘焦点样式不统一

登录页定义了 `:focus-visible`，大部分工作区按钮和链接依赖浏览器默认焦点，视觉一致性和可见性不可控。

### L4. “归档记录”文案被误用于删除处方药品行

处方编辑中的行移除按钮只是删除当前未提交行，却显示“归档记录”，语义错误。应改为“移除此药品”。

### L5. 今日接诊数量和空状态文案不准确

删除“已完成/已撤回”筛选后，标题人数仍统计全部预约；两个剩余筛选共用“当前暂无接诊患者”，没有对应“待接诊/接诊中”。

## 按流程健康度

1. **登录与注册：风险较高**
   - 主流程完整，但明文密码、弱默认密码、邮箱丢弃和错误状态码需要处理。
2. **管理员基础资料维护：风险较高**
   - 增删改查齐全，但“归档”是物理删除，缺少关联保护。
3. **患者 AI 问诊：需要整改**
   - 有免责声明和本地回退，但第三方数据处理缺少明确同意，AI 记录与预约没有正确关联。
4. **预约挂号与取消：需要整改**
   - 基本校验可用，但并发重复预约、状态机和接诊中取消存在问题。
5. **医生接诊工作台：基本可用但数据规则不足**
   - 前端闭环检查较完整，服务端可绕过，且页面文件过大。
6. **病历、处方与检查：基本可用但追溯性不足**
   - 角色级数据所有权检查总体存在；缺少外键、审计日志、版本历史和并发库存保护。
7. **患者结果查看：基本可用**
   - 数据按患者隔离，但进度中的 AI 步骤可能串到其他预约。
8. **全局导航和角色隔离：需要整改**
   - 后端多数接口有角色保护，前端 query workflow 没有角色白名单。
9. **响应式和无障碍：需要专项回归**
   - 有部分响应式规则和登录页焦点处理，但侧栏顺序、状态语义和实时消息不完整。
10. **工程质量与部署准备：不合格**
   - 零测试、无 lint、依赖漏洞、配置凭据和文档漂移阻止安全部署。

## 建议修复顺序

### 第一批：立即处理

1. 撤销并移除代码中的外部 API 凭据。
2. 密码迁移到 BCrypt/Argon2，取消统一默认密码。
3. 把所有“归档”改为软删除，停止物理删除历史主体。
4. 增加数据库外键、预约唯一控制和库存原子扣减。

### 第二批：保证业务正确

1. 服务端预约状态机和取消规则。
2. AI 问诊与具体预约绑定。
3. 前端 workflow 角色白名单。
4. 标准 HTTP 状态和安全异常处理。

### 第三批：提升可维护性和体验

1. 补集成测试、前端测试、lint 和 CI。
2. 修复依赖漏洞、README 和注册字段。
3. 分页、表单限制、无障碍语义和窄屏侧栏。
4. 拆分大型组件并引入数据库迁移工具。

## 证据限制

本次审查完成了源码、构建、依赖和 API 行为检查。Codex 内置预览页崩溃，Chrome 又因本地 URL 安全策略拒绝自动化，因此无法对每个页面保存现场截图，也没有验证真实键盘导航、屏幕阅读器、颜色对比和所有视口下的视觉效果。视觉相关结论应在浏览器可访问后补一次逐页回归。
